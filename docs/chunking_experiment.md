## Итоговый выбор

Для экспериментального retrieval-пайплайна выбираю semantic с дополнительным recursive-разбиением фрагментов длиннее 512 токенов, перекрытием 32 и top-K = 10 уникальных багов.

Коллекция: docs_semantic_s512_o32.
Embedding-модель: text-embedding-3-small.
Re-ranker: BAAI/bge-reranker-v2-m3, локально на CPU.

На 24 эталонных вопросах получены:
- Hit Rate@5 = 1.0000;
- MRR@10 = 0.9479;
- Recall@10 = 1.0000.

Без re-ranker Hit Rate@5 составлял 0.9167, MRR@10 — 0.8601. Re-ranker улучшил положение релевантных багов в выдаче. Обрезки входных пар не было.

Ограничение 256 токенов ухудшило MRR без улучшения остальных метрик. Ограничение 512 сохранило исходные semantic-фрагменты.
Преимущество перекрытия 32 над 64 не доказано: на текущем корпусе при ограничении 512 дополнительное
разбиение не потребовалось.

Среднее время поиска с re-ranker составило 11.16 секунды против 24.75 мс без него. Поэтому конфигурация выбрана
по качеству для эксперимента, но пока не включается в рабочий поиск оператора.

Результаты получены на наборе, использованном для подбора параметров. Следующая проверка качества должна проводиться на новых обращениях без изменения их эталонной разметки под результаты поиска.

## Фиксация конфигурации

Выбранные параметры сохранены в .env / .env.example
и представлены полями Settings в app/core/config.py:

- RETRIEVAL_STRATEGY=semantic_recursive;
- RETRIEVAL_COLLECTION=docs_semantic_s512_o32;
- RETRIEVAL_CHUNK_SIZE=512;
- RETRIEVAL_CHUNK_OVERLAP=32;
- RETRIEVAL_TOP_K=10.

Параметры re-ranker сохранены отдельно в RERANKER_*.

Скрипт evaluate_reranker.py по умолчанию читает выбранную коллекцию и top-K из настроек.

Рабочий Telegram-бот и endpoint /rag/query не переключены на экспериментальную конфигурацию. Изменение настроек не выполняет автоматическую переиндексацию.
