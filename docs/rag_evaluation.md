# Оценка качества и мониторинг RAG

## Golden dataset и ручная проверка

Итоговый набор содержит 32 вручную проверенных примера.
Ассистент оценивается как поиск известных багов по обращениям клиентов, а не как система консультаций.
Файлы загружаются в репозиторий вручную.
Отдельного коммита, показывающий переход от автогенерации к исправленному набору, нет.
Вместо него представлены исходный и проверенный файлы, а также примеры содержательных исправлений ниже.

Артефакты:
- исходная автогенерация:
  tests/eval/golden_dataset_raw.csv;
- версия после ручной проверки:
  tests/eval/golden_dataset_reviewed.csv;
- итоговый набор, использованный в оценивании:
  tests/eval/golden_dataset.json.

Проверялись соответствие обращения документам, корректность reference и reference_contexts.
Реальные неоднозначные формулировки сохранялись, вопросы не упрощались ради повышения метрик.

### Примеры ручной правки

## Baseline

Прогон: 20261002_171215_989239_baseline.
Проверено 32 примера. Все четыре метрики рассчитаны без пропусков.

| Faithfulness | Answer relevancy | Context precision | Context recall |
|---:|---:|---:|---:|
| 0.7868 | 0.1794 | 0.8046 | 0.7927 |

Источник чисел:
tests/eval/results/20261002_171215_989239_baseline_summary.json

Faithfulness превышает порог ТЗ 0.7.
Answer relevancy ниже порога 0.7 и требует разбора отдельных ответов.

Проверяемая гипотеза: стандартная метрика релевантности ответа может штрафовать выдачу карточек багов вместо прямого ответа на вопрос клиента. Назначение ассистента при этом не меняется:
он ищет известные баги, а не консультирует по общим вопросам.


## Разбор baseline

Эталонный номер бага присутствует в 26 из 32 ответов (81,25%).
Это не метрика RAGAS и не оценка точности полного списка выданных багов, а лишь проверка наличия номера в ответе.

В примерах 3 и 11 эталонные карточки присутствуют в контексте, но система возвращает отказ. Требуется проверка этапа генерации и достаточности описания для сопоставления.

В примере 29 эталонный баг 121 отсутствует в итоговом контексте, хотя карточка есть в учебном корпусе. Требуется проверка retrieval и re-ranking.

Для примеров 27, 31 и 32 требуется проверить наличие карточек 167, 154 и 160 в активной коллекции.

Низкая answer_relevancy наблюдается и при правильном номере бага.

## Изменение системного промпта

Вместо балльной шкалы 0–5 используется смысловое сопоставление обращения с названием и описанием бага.

Общие значения темы и влияния не считаются самостоятельным подтверждением совпадения. Закрытый статус и старая дата создания не исключают баг, если его симптомы соответствуют обращению.

Сохранены две группы результатов, установленный формат, цитирование и отказ «Подходящих багов не найдено».

Golden dataset не изменён. 

Качество нового промпта пока не измерено повторным прогоном. Ранее полученные метрики относятся к прежнему промпту.

Изменено только правило заполнения поля «Причина»: использовать «Тема» из документа, не подменять её симптомами или влиянием бага.

## Failure analysis

Источник: 20261003_233321_228130_chunk512_no_reranker.json.
F — faithfulness, CR — context_recall.

| Обращение | Найденный контекст | Ответ | F / CR | Предварительный диагноз |
|---|---|---|---|---|
| Про оплату РТР после двух месяцев работы | Баг 103 присутствует | Подходящих багов не найдено | 0 / 0.8333 | Проверить решение генератора отклонить найденный баг; обращение неоднозначно |
| Что можно сделать, если подключение к ЭЦП отсутствует? | Баг 109 первым, также присутствует 118 | Подходящих багов не найдено | 0 / 0.8000 | Вероятный избыточный отказ генератора при наличии подходящего контекста |
| Не могу продать товар, не пробивается | Эталонного бага 121 нет | Подходящих багов не найдено | 0 / 0 | Проблема поиска/отбора контекста; запрос очень общий |
| Ошибка java что это, как решить? | Баг 154 присутствует | Подходящих багов не найдено | 0 / 0.8000 | Проверить правила сопоставления неполного обращения с документом |

Нулевая faithfulness у отказа не означает автоматически галлюцинацию. Диагноз учитывает сам ответ и найденные документы, а не только числовую оценку.

Основные причины ошибок: избыточные отказы генератора при наличии подходящего контекста и отдельные промахи retrieval на слишком общих обращениях. Отключение re-ranker ускоряет ответы, но не даёт устойчивого улучшения качества.

## Финальная конфигурация и известные проблемы

Для локального запуска выбираю:
semantic_recursive,
chunk_size=512, 
overlap=32, 
retrieval top-K=10,
context top-N=5, 
без re-ranker.

Основание: среднее время 3.18 секунды вместо 11.51, при близких агрегированных метриках качества.

Faithfulness=0.7043 проходит порог задания. 
Answer relevancy=0.2062 и has_citation=0.8750 порогов задания не достигают.

Все четыре ответа без цитат являются отказами.
Добавлять к ним фиктивные ссылки нельзя.

Известные проблемы: избыточные отказы при наличии эталонного бага в контексте и пропуск бага 121 на этапе поиска. Стандартная answer_relevancy может быть плохо применима к ответам в виде списка багов, это остаётся гипотезой.

## Проверка Phoenix

Phoenix запущен локально, отдельно от backend.
Выполнено 20 разнообразных обращений через Telegram.

Подтверждены операции:
- RAG Telegram — общий трейс обработки обращения;
- CreateEmbeddings — получение эмбеддингов новых запросов;
- RAG retrieval — найденные фрагменты, идентификаторы и scores;
- ChatCompletion — промпт и расход токенов.

Retrieval записывается явно через OpenTelemetry с атрибутами
OpenInference. Показаны кандидаты до re-ranker и score-guard.

Для повторных запросов эмбеддинги могут браться из кеша.
При кодовом отказе генерация не вызывается.

Во время проверки зафиксированы таймауты:
- CreateEmbeddings: APITimeoutError, длительность операции 31.4 с, id трейсов: 4f15e9b84e2e1e7bd0b1653904017159, 4f15e9b84e2e1e7bd0b1653904017159;
- ChatCompletion: ReadTimeout, длительность операции 54.6 с. id трейсов: 4f15e9b84e2e1e7bd0b1653904017159,4f15e9b84e2e1e7bd0b1653904017159.

Точная причина задержек не установлена. При прерывании запроса бот показывает сообщение «Не удалось завершить поиск. Попробуйте позже». При повторном таком же запросе ошибка не воспроизводилась.

Скриншоты сохранены в docs/screenshots/.
Запуск Phoenix через Docker Compose локально не проверен из-за технических ограничений.

## Известные проблемы
Дополнительно по ручной проверке:
- иногда выводится пустой раздел «Менее релевантные баги»;
- понимание уточнений ограничено списком фраз;
- встречаются таймауты получения эмбеддингов и генерации.

## Итог выполнения

Выполнены оценивание 32 примеров, два A/B-эксперимента, разбор ошибок и проверка Phoenix на 20 обращениях. В трейсах видны поиск, эмбеддинги и генерация.

Ограничения:
- answer_relevancy и has_citation ниже целевых порогов;
- запуск Docker Compose локально не подтверждён;
- форма подтверждения ручной вычитки требует согласования;
- обнаружены пустые разделы ответа и случаи сетевых таймаутов;
- понимание уточнений пока ограничено списком фраз.

HallucinationEvaluator — необязательный этап, не выполнялся. Риск галлюцинаций оценивался через RAGAS faithfulness, которая проверяет опору ответа на найденный контекст.
