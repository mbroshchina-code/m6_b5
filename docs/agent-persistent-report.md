# Persistent-граф с выбором временного решения человеком

## 1. Backend и версии

Локально используется AsyncSqliteSaver:
var/agent/workarounds.sqlite3.

Для контейнерного режима предусмотрен AsyncPostgresSaver.
Memory используется только для неперсистентных экспериментов.

Фактически установленные версии получены командой через
importlib.metadata.version:

```text
langgraph==1.2.12
langgraph-checkpoint-sqlite==3.1.2
langgraph-checkpoint-postgres==3.2.0
aiosqlite==0.22.1
psycopg==3.3.6
psycopg-pool==3.3.3
```

SQLite выбран для локальной разработки: не требует отдельного сервера
и сохраняет состояние в файле между запусками приложения.
Postgres предусмотрен для контейнерного режима.

Старый agent_graph.py сохранён.
Основной системный промпт баг-ассистента не изменён.
Новый граф сохраняет поиск и проверку ответа критиком.
Отправка выполняется отдельным управляемым сценарием.

## 2. Postgres и Compose

Для контейнерного режима подготовлен docker-compose.yml:
сервисы app, bot, qdrant, redis и postgres.

В сервисе app заданы:
- AGENT_CHECKPOINTER=postgres;
- POSTGRES_HOST=postgres;
- POSTGRES_PORT=5432.

Имя базы, пользователь и пароль читаются из POSTGRES_*.
Обезличенный URI:
postgresql://<user>:<password>@postgres:5432/<database>

Для checkpoint-таблиц отдельная база не создаётся:
используется база из POSTGRES_DB.
Хранилище истории чатов в текущей реализации остаётся JSONL.

В проекте также есть compose.yaml с отличающимся составом сервисов.
Для описанного режима с Redis используется явно выбранный
docker-compose.yml.

Явный await saver.setup() выполняется один раз при входе
в agent_lifespan для SQLite или Postgres.
На HTTP-запросах setup() не вызывается.
Для memory этот вызов не требуется.

Alembic в текущем проекте отсутствует.

Docker локально не работает, поэтому пока не проверены:
- запуск приложения с AsyncPostgresSaver;
- создание checkpoints, checkpoint_writes,
  checkpoint_blobs и checkpoint_migrations;
- сохранение и продолжение паузы после перезапуска контейнера.

Это незакрытая проверка контейнерного режима.
Локальная проверка SQLite не заменяет проверку Postgres.

## 3. Опасный инструмент и идемпотентность

Опасный инструмент — send_workaround.
Он передаёт временное решение во внешний Telegram-чат.

Оператор сначала выбирает релевантный баг,
затем подтверждает точный текст и получателя.

Первая пауза — select_workaround.
Вторая пауза — approve_send_workaround.

Интерфейс оператора на этом этапе — API/curl.
Список багов и варианты выбора возвращаются оператору через SSE.
В существующего Telegram-бота передаётся только исходное временное
решение выбранного бага после отдельного подтверждения отправки.
Кнопки выбора и подтверждения в Telegram пока не реализованы.

До interrupt:
- выполняется поиск;
- формируется и проверяется ответ для оператора;
- сохраняются исходные найденные карточки;
- из релевантных багов формируются варианты с временными решениями;
- сохраняется выбор человека;
- отдельный узел prepare_send создаёт draft;
- action_id детерминированно вычисляется из идентификаторов,
  версии источника и draft;
- внешняя отправка не выполняется.

После interrupt:
- проверяется строгое положительное решение;
- вызывается send_workaround;
- при подтверждённом успехе сохраняется sent=True.

Между prepare_send и confirm_and_execute_send есть отдельное ребро.

В Telegram отправляется только исходный текст выбранного решения.
Ответ модели, список багов и служебные статусы не отправляются.

Чтение прошлого checkpoint показывает:
- выбранный баг;
- подготовленный draft;
- sent=False;
- следующий узел подтверждения.

PAST: draft = {'chat_id': 'test_chat_id', 'text': 'Выполнить демонстрационное действие Б.\nСохранить результат.'} sent = False next = ('confirm_and_execute_send',)

Replay выполняется через ainvoke(None, checkpoint_config).
Отказ и одобрение показываются на разных thread_id
с одинаковым исходным input и одинаковым выбранным багом.

Повторное resume уже обработанного interrupt
не используется для изменения решения.

Фактический результат офлайн-демо:

```text
REPLAY: ('confirm_and_execute_send',)
RESULT: False rejected 900002
RESULT: True sent 900002
External API calls: 0
Mock received only the original solution of bug 900002.
```

Решение resume сохраняется для соответствующего interrupt.
Для демонстрации противоположных решений используются разные
thread_id с одинаковыми исходными данными, а не повторное
подтверждение уже обработанной паузы.

Полный вывод: [agent-persistent-demo.log](agent-persistent-demo.log).

## 6. Streaming

Используется astream(stream_mode=["updates", "messages"]).

updates показывает прогресс узлов и паузы.
messages передаёт части генерации модели.

Выбран astream(stream_mode=["updates", "messages"]):
эти режимы дают нужный прогресс узлов и части ответа модели.
astream_events(version="v2") не используется, поскольку подробные события всех вложенных вызовов для текущего интерфейса не требуются.

Промежуточные токены обозначены draft_token.
Итоговый список для оператора находится в operator_answer.
Успешно отправленное решение находится в client_text.

Служебные оценки критика не выдаются как ответ.
При паузе SSE-запрос завершается; следующий запрос
с тем же thread_id продолжает сохранённый граф.

## 7. Permission policy

Роль берётся из серверной настройки: read-only запрещает отправку,
write-with-approve и full требуют выбора и подтверждения;
API защищён ADMIN_TOKEN.

## 8. Ограничения и дальнейшие улучшения

- Реализован режим одного worker и одного активного запуска.
- Для нескольких процессов нужна общая блокировка.
- Общий ADMIN_TOKEN не заменяет персональную авторизацию операторов.
- Парсер полей рассчитан на текущий формат карточек.
- Нужно расширять проверки для новых форматов документов.
- Решение сохраняется как снимок источника:
  последующее изменение базы не меняет уже показанный preview.
- Длинные решения не отправляются автоматически и не обрезаются.
- При сетевом сбое доставка может иметь статус unknown.
- Детерминированный action_id не обеспечивает exactly-once доставку.
- Авария после внешней отправки, но до сохранения результата
  требует отдельной процедуры проверки доставки.
- История диалога пока не ограничена по размеру.
- Выбор и подтверждение через кнопки Telegram,
  а также подключение входящих сообщений бота к этому графу
  остаются отдельной интеграцией.
- Docker/Postgres: конфигурация подготовлена, запуск и восстановление после перезапуска контейнера не подтверждены.
- Проверка «релевантный баг без временного решения» не выполнена:
  в trainings_bugs нет подходящего примера.
  Планируется офлайн-тест с искусственной карточкой без решения;
  менять рабочую базу для этого не требуется.
- Проверка «только менее релевантные баги» не выполнена.
В доступной версии системного промпта этот раздел допускается в ответе оператору, но такие баги исключаются из вариантов отправки. Требуется согласовать это с желаемым запретом их отображения.
- По результатам ручной проверки остальные проверенные сценарии отработали корректно: сторонний запрос, использование истории, отсутствие придуманных сроков, отсутствие совпадений, отклонение чужого номера бага и повторного подтверждения.
