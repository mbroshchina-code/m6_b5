# Сравнение single-agent и multi-agent

## Сценарий

Вход — обращение оператора о проблеме клиента с доступной историей.
Researcher ищет карточки и возвращает факты с источниками.
Writer проверяет факты по источникам и оформляет ответ оператору.
Выход — группы багов с номерами, названиями, статусами, причинами,
временными решениями и цитатами [1], [2]; при отсутствии совпадений
строго «Подходящих багов не найдено».

Single-agent выполняет обе роли с тем же поисковым инструментом.

## Тестовые вопросы

- Q1 (corpus): При продаже на чеке появляется уведомление «Чек аннулирован», но после этого чек успешно фискализируется и печатается. История: нет Ожидаемые баги: 112.
- Q2 (corpus): При регистрации в Милена ЭДО возникает ошибка «Некорректный статус регистрации.». История: нет Ожидаемые баги: 110.
- Q3 (corpus_with_history): Что мне делать? История: не работает интернет на оплаченных сим-картах Лучи. Ожидаемые баги: 101.
- Q4 (multistep): Два вопроса. Первый: при продаже появляется «Чек аннулирован», затем чек успешно печатается. Почему так? Второе: при регистрации в Милена ЭДО появляется «Некорректный статус регистрации. Текущий статус INS, должен быть ARED».  История: нет Ожидаемые баги: 112, 110.
- Q5 (out_of_base): После обновления касса выдаёт ошибку E-9999. История: нет Ожидаемые баги: нет.

Q4 проверяет разбор двух описаний проблем в одном обращении:
нужно выделить обе проблемы, сопоставить каждую с карточкой
и собрать общий ответ. Это составная задача, а не проверка
обязательной последовательности зависимых поисковых запросов.
В сохранённом прогоне multi-agent сделал два вызова поиска,
single-agent — один; обе реализации нашли нужные карточки.

## Реализация

Использован ручной supervisor на LangGraph с Command.
Порядок стадий известен заранее, поэтому supervisor не вызывает LLM.
Это эксперимент с фиксированной политикой координации двух агентов,
а не с динамическим планированием supervisor-моделью.

Researcher и writer созданы через langchain.agents.create_agent.
У researcher один tool search_knowledge_base, у writer tools=[].
Одинаковая реализация поиска используется single-agent.
Поиск вызывает CitationRAGService.prepare_context и не генерирует
ответ скрытым дополнительным вызовом LLM.

Модель исполнителей: gpt-5.4-mini.
Версии библиотек: {"langgraph": "1.2.12", "langchain": "1.4.3", "langchain-core": "1.6.6", "langchain-openai": "1.6.6"}.

Используется активная ingestion-коллекция из настроек проекта.
Конфигурация, отпечатки индекса, кода и эталонов сохранены в results.json.
Прокси применяется через существующую фабрику make_graph_model.

Координация — shared state, выделенная область research с facts и sources.
Writer получает исходное обращение, факты и исходные найденные документы.
Полные внутренние истории двух агентов друг другу не передаются.

Общий лимит — 6 LLM-вызовов на запрос.
Для multi: researcher до 5, writer до 1; supervisor — 0.
Лимит поиска — 3 вызова для обеих реализаций.

## Методика измерений

Основной запуск — python -m experiments.run_benchmark.
Реализации выполняются последовательно, их порядок чередуется.
Перед измерениями выполнен один прогревочный запрос к RAG.
Re-ranker в данном эксперименте отключён:
в metadata всех запусков сохранено reranker_enabled=false.
В latency входят поиск, LLM, выполнение графа и получение
финального состояния; импорты, сборка графа и прогрев не входят.

На каждый вопрос создаётся новый граф с новым InMemorySaver.
thread_id="exp-langgraph"; повторное имя не смешивает вопросы,
поскольку каждый saver принадлежит отдельному запуску.
Прогресс выводится через app.stream(stream_mode="updates").
Схема сохраняется результатом app.get_graph().draw_mermaid().

total_tokens суммирует input + output всех LLM-вызовов реализации.
llm_calls учитывает также вызовы, сформировавшие tool calls.
Модельного supervisor-роутинга в выбранной реализации нет.
Токены embedding API и судьи в основные метрики не включены.
Токены — показатель объёма обработки, а не полный счёт в деньгах.

handoff_count считает передачи supervisor → worker и worker → supervisor.
У завершённого multi-запроса их 4, у single — 0.
Вызовы tools и переходы START/END сюда не входят.

Качество — доля ответов, прошедших все пять критериев LLM-судьи:
подбор багов, правильность полей, цитирование, формат, отсутствие выдумок.
Судья получает эталонные карточки независимо от результатов поиска.
Название архитектуры судье не передаётся.
Модель судьи — gpt-5.4; затраты сохранены отдельно в поле judge.
Результаты судьи требуют ручной проверки по карточкам.

## Результаты

| Метрика | Single-agent | Multi-agent | Δ multi − single |
|---|---:|---:|---:|
| Токены на запрос, среднее | 7303.20 | 12383.40 | +5080.20 |
| LLM-вызовы на запрос, среднее | 2.00 | 3.00 | +1.00 |
| Latency p50, мс | 4480.08 | 5318.24 | +838.16 |
| Передачи управления на запрос, среднее | 0.00 | 4.00 | +4.00 |
| Качество по LLM-судье, % | 100.00 | 80.00 | -20.00 |

Δ качества выражена в процентных пунктах.

На этих пяти примерах multi-agent снизил долю правильных ответов на 20.00 п. п.
Отношение средних токенов multi/single равно 1.70×.
Отношение latency p50 multi/single равно 1.19×.
Для данной задачи роли последовательно используют общий контекст;
пять вопросов и один прогон дают предварительный результат,
а не статистическое доказательство превосходства архитектуры.

Ручная проверка ответов подтвердила итоговую оценку LLM-судьи:
single-agent — 5 правильных ответов из 5, multi-agent — 4 из 5.
На Q1–Q4 обе реализации нашли ожидаемые карточки и корректно
указали источники, включая обращение с историей и два разных
описания проблем в одном сообщении.

На Q5 single-agent вернул «Подходящих багов не найдено».
Multi-agent предложил баг 105 об ошибке загрузки данных 400
для обращения об ошибке E-9999. Ссылка ведёт на существующую
карточку, но её соответствие обращению не подтверждено.
Это ошибка подбора бага, а не выдуманная карточка или источник.

## Сопоставление с Anthropic

В публикации Anthropic от июня 2025 описаны +90,2% на внутренней
исследовательской оценке относительно single-agent и около 15×
токенов относительно обычного чата. Это разные базы сравнения.
Наш множитель 1.70× относится к multi/single с одинаковой моделью.
Наш поиск по общей базе багов отличается от breadth-first research
с независимыми параллельными направлениями.
Anthropic также отмечает ограничения при общем контексте
и сильной зависимости задач друг от друга.

Источник:
[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system).

## Решение

**Не использую мультиагентность в дипломе.**

По оценке LLM-судьи, подтверждённой ручной проверкой, single-agent
правильно обработал 5 из 5 случаев (100%), multi-agent —
4 из 5 (80%). При этом multi-agent потребовал в среднем
12 383,40 токена против 7 303,20 у single-agent (+69,56%).
Latency p50 выросла с 4 480,08 до 5 318,24 мс (+18,71%),
число LLM-вызовов — с 2 до 3, передач управления — с 0 до 4.

Для баг-ассистента поиск и оформление ответа последовательно
используют общий контекст карточек. В этом эксперименте разделение на researcher и writer увеличило затраты и не улучшило качество.
Это согласуется с ограничениями мультиагентности при общем
контексте и зависимых задачах, рассмотренными в публикации
Anthropic, указанной в предыдущем разделе.

Из двух исследованных реализаций выбираю single-agent с инструментом search_knowledge_base. Supervisor-граф остаётся в experiments/ и не переносится в app/agents/.

Для своего итогового проекта принимаю отдельное
архитектурное решение - сохраняю управляемый RAG:
учёт истории → поиск карточек → сопоставление с обращением
и формирование ответа в установленном формате.
Автономный агентский цикл пока не добавляю: последовательность
работы известна заранее, статусы и временные решения нужно сохранять точно, дополнительная передача через пересказ researcher увеличивает риск искажений, история нужна независимо от агентности. При этом текущий эксперимент не доказывает необходимость агентского цикла по сравнению с существующим RAG.

Решение принято по пяти вопросам и одному прогону без re-ranker.


## Ограничения

- Пять случаев, по одному запуску каждой реализации.
- Измерения выполнены без re-ranker; задержку при его включении этот эксперимент не оценивает.
- Кеш эмбеддингов сохраняется; порядок реализаций чередуется,
  но при пяти случаях баланс порядков не идеален.
- Оценка LLM-судьи может содержать ошибки.
- Результаты относятся к ручному supervisor без LLM-роутинга.
- Сравнение single и multi не доказывает преимущество агента
  над существующим управляемым RAG.
- Отдельные проверки сторонних запросов и других вариантов истории нужны перед включением выбранного решения в приложение.
